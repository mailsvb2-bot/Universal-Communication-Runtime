# ADR-0018: Runtime receipts and generic acknowledgements preserve wire semantics

Status: Accepted

## Context

The public `ucr.v1` protobuf contract defines `CommandReceipt` and `AcknowledgementEnvelope` with explicit `schema_version` and repeated protocol `extensions`. The Rust reference implementation historically modeled only receipt status/provenance, while generic acknowledgement existed only as protobuf plus `FrameKind::Acknowledgement`. This created another public-contract parity gap after Command/Event parity hardening.

A second risk is semantic confusion: UCR Delivery has a durable `ACKNOWLEDGED` state that requires transport-acceptance evidence, while the generic runtime acknowledgement is only a protocol response for an opaque object ID.

## Decision

`ucr-protocol` owns canonical Rust types and validation for both runtime response envelopes. `CommandReceipt` carries command ID, receipt status, optional original command ID, schema version, and canonical protocol extensions. `AcknowledgementEnvelope` carries acknowledged opaque ID, schema version, and canonical protocol extensions.

Both envelopes require a non-zero schema major, enforce shared extension namespace/count/payload rules, reject duplicate extension names, and canonicalize extension order lexically by name. Base responses generated by the reference runtime use `RUNTIME_ENVELOPE_SCHEMA_V1` (`1.0`) with an empty extension set. Request extensions are not copied into responses implicitly.

A generic acknowledgement confirms only that the identified protocol object was acknowledged at the enclosing protocol layer. It is not an Event and is not evidence of provider acceptance, transport acceptance, device delivery, user delivery/read, or an external side effect. `DeliveryState::Acknowledged` remains a separate evidence-gated durable concept.

Command acceptance stores do not persist receipts as a second durable record. They persist canonical command acceptance first, then construct the base receipt from protocol-owned constructors. Duplicate receipts remain derivable from durable accepted-command state.

## Consequences

Rust and protobuf now agree on the complete public shape of Command receipts and generic acknowledgements. Memory and SQLite cannot silently emit response envelopes without explicit version metadata. Generic ACK can no longer remain an untyped frame payload in the Rust reference contract.

No SQLite schema change is required because response envelopes are derived protocol output, not additional canonical durable state.

## Rejected alternatives

- Copy Command extensions into CommandReceipt: rejected because request metadata is not automatically response metadata.
- Treat generic ACK as Delivery `ACKNOWLEDGED`: rejected because that would bypass typed transport evidence and inflate delivery state.
- Persist every receipt separately: rejected because durable command acceptance already owns duplicate provenance and a second store would duplicate canonical state.
- Keep protobuf-only acknowledgement semantics: rejected because the Rust reference implementation must not silently omit a stable public envelope.
