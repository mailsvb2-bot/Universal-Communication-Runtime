# UCR Protocol Specification

The `spec/` directory is normative protocol design material. Rust structures are a reference implementation mapping only.

The protocol must cover identity, principal, actor, device, endpoint, addressing, handshake, commands, events, messages, conversations, groups, calls, media, attachments, delivery, sync, permissions, policy, crypto negotiation, capability negotiation, errors, extensions and version negotiation.

Phase 0 defines common envelopes and negotiation rules first. Later phases refine entity-specific semantics without replacing the fundamental model.

Phase 13 adds the first external-consumer boundary in `integration-api.md`; it reuses canonical Commands, Identity/Conversation/Message/Communication Intent owners and Service Principal admission rather than exposing Rust/storage internals. Phase 14 adds `event-api.md`: a separate eight-RPC `EventService` over the one canonical append-only Event journal plus durable consumer cursor/retry/replay/dead-letter state. Generated Rust/Tonic code is not normative protocol logic. Phase 15 adds `internet-transport.md`: a Prepared concrete `TransportProvider` over public-IP TCP that reuses canonical negotiation/Crypto/trust owners and does not own routing orchestration. Phase 16 adds `local-transport.md` as the distinct Prepared local/direct transport path while retaining the same canonical transport and crypto owners. Phase 17 adds `chat.md` as the Prepared direct-chat layer over canonical Conversation, Message, Delivery and authorization owners. Phase 18 adds `groups.md`: provider-independent Group membership, roles, ownership, history/public policy, restart-safe SQLite v21 state, and membership-gated access to the existing canonical Message owner without a second Conversation/Message brain. Phase 19 adds `call-signalling.md`: restart-safe transport-independent CallSession signalling over canonical Conversation/Principal/Group/authorization/Event owners. Phase 20 adds `audio.md`: Prepared realtime Opus encode/decode over the same Call/Group/authorization owners and the canonical Capability model. Phase 21 adds `video.md`: Prepared realtime H.264 camera/screen-share encode/decode over the same Call/media-negotiation/authorization owners. Phase 22 adds `media-e2ee.md`: Prepared direct-call authenticated media encryption/replay/key-rotation semantics over the same Call/Crypto/Capability owners, with group media failing closed until a standardized group-key owner exists. Phase 23 adds `adaptive-media.md`: bounded resource/network observations, graceful quality degradation, hysteresis, existing Video/Audio controls and a deferred eventual-continuity boundary without route selection. Phase 24 adds `transport-orchestrator.md`: bounded transient candidate validation, hard Intent/Policy/Endpoint/provider filtering, deterministic ranking and single-primary execution. Phase 25 adds `transport-failover.md`: bounded sequential cross-route execution that advances only after provider-proven non-acceptance and stops conservatively on ambiguous acceptance. Phase 26 adds `offline-groups.md`: one-hop authenticated Device-peer Group/Message reconciliation over the existing Sync and canonical storage owners, restart-safe SQLite v23 sidecars, delayed/history-aware Message acceptance, and no re-export of remote records. Phase 27 adds `store-forward.md`: bounded sender-side durable retry over canonical Intent/Message/Delivery/Transport owners, SQLite v24 restart-safe scheduling and completion tombstones, one provider invocation per Delivery ID, and conservative blocking on ambiguous `InFlight` acceptance. Phase 28 adds `mesh.md`: bounded loop-free multi-hop propagation of signed Group Messages over existing PeerPeer Sync/Crypto trust, with SQLite v25 path metadata and no Relay/discovery/topology owner. Phase 29 adds `sfu.md`: Prepared RFC-9420/OpenMLS-backed group-media E2EE and SFU fan-out over canonical Group/Call/Device/permission owners, SQLite v26 atomic Group↔MLS transitions, explicit Principal→Identity association, source-Device signatures and no plaintext, Conference, durable-route or Delivery authority. Phase 30 adds `conference.md`: Prepared Conference coordination over existing Group/Call/Audio/Video/MLS/SFU owners, a shared bounded 1024-participant ceiling with executable 1000-accepted-participant reference evidence, and recipient-owned ephemeral subscriptions capped at 32 source/media pairs without a second durable Conference roster or authorization brain. Phase 31 adds `bridge-sdk.md`: a provider-agnostic Bridge extension/trust boundary with explicit manifest capabilities/data permissions, restart-safe SQLite v27 registration/action metadata, classified provider acceptance, fail-closed `NoExternalBridge`, and bounded inbound event pages without a second Message/Delivery/Identity brain.
